# 审一个模型

产出是一份能过 `validate.py` 的记录，且**每个数字都能追到你本次真正读过的源**。

失败模式不是「写得不够全」，是**写了个看起来对的错数字**。留空会被下游看见，错数字不会 ——
它会被当成事实引用、进族谱、进简报。本仓已有的错数字没有一个是编的，全是「验了一个因子就报出去」。
所以这个 skill 讲的是怎么核实，不是怎么排版。

案例史在 [README.md](../../../README.md) 的「用例」一节，按发现顺序记着每个错数字的来龙去脉。
规则在下面，案子在那里，**不要在记录里重写案子**。

## 取数顺序

脚本用法与参数在 README 的「用法」一节。这里只说顺序和取舍：

1. **清单**：旗舰才值得全量清单（`fetch_hf.py`）。同族系的版本先用 `--names-only` 比张量名集合 ——
   集合相同就不必重走算子评估，这是整个跟踪里最省力的一个判据
2. **草稿**：`scaffold.py` 从 config 生成，**它的判型会错**（规则 2）。草稿是填空位，不是结论
3. **精度**：`fetch_dtypes.py` → `apply_dtypes.py`（对已有值默认只比对不覆盖）
4. **缓存宽度**：`fetch_kv_widths.py`，钉 `--rev`。它的 `CLASSES` 是 DeepSeek V4 一代的张量名，
   别的族系用 `--pattern KEY=REGEX` 追加；`lib/subsystems.py` 的归类正则可能也要扩
5. **对账**：`derive.py` 两路算同一个量（公式路 / 权重路），不一致就报、不替你选边 —— 这是 Gate B
6. **校验**：`validate.py`，然后 `--list-judgements` 看判断类字段
7. **改过缓存数就跑 `kv_table.py`** 重生成 docs 里的跨族系对照表（`--check` 查过期）
8. 需要逐层图再 `extract_layers.py`

## 缓存账的提问顺序

显存账是这个仓库最容易错的地方，错过的每一次都是下面某一问没问。按顺序过，每一问都写下答案的来源。

1. **分几类缓存？** 全局 KV / 索引 / 滑窗局部 / 线性注意力递归状态 / 其它。
   **混合结构必须分两个分量**：随上下文线性增长的（`per_token_bytes`）与每序列固定的
   （`per_sequence_bytes`）。合成一个数表达不了，Qwen3.8 就是这么逼出重构的
2. **每类的产出张量是谁？** 缓存宽度是**产出它的张量的输出维**，不是 config 里的头数乘积。
   index K 在 index 头之间 MQA 共享，按 `index_n_heads × index_head_dim` 算高估 32 倍
3. **条目宽度逐层量，同类内一致吗？** 不一致则「宽度 × 层数」这个乘式本身不成立，折算要重做。
   `fetch_kv_widths.py` 会检查并报出来 —— 它报不一致时不要改脚本去绕
4. **一个条目覆盖几个 token？** per-token / 按压缩比折算 / per-sequence 固定。
   把每序列固定的滑窗 KV 逐 token 计费，是 5.2 倍高估里的一个因子
5. **每元素几字节？有一手来源吗？** 没有就按模型 dtype 兜底并标 `bytes_basis: dtype_fallback`，
   同时留一条 open question。**不要用兜底值去和别人的精确值比**
6. **层覆盖：哪些层产出、哪些层读？** 三类缓存的覆盖面通常互不相同。
   **「逐层」这个词正是上一轮 5.2 倍高估的源头**，写记录时写明确的层集合
7. **跨代/跨族系比之前：两侧 basis 是同一套吗？** 不同就换元素口径（与精度无关）。
   `data.ts` 的 `diff: 'same-basis'` 守卫做这件事，但只管页面，不管你在正文里写的倍数

口径定义与一份逐格填满的示例见 [docs/kv-cache-accounting.md](../../../docs/kv-cache-accounting.md)。

## 读证据的规则

**1. 一个乘式逐因子验。** 报出一个乘积前，把每个因子单独写出来源。本仓同一个 KV 乘式被改过四轮，
每轮都是「上一轮只验了一个因子」：哪些层 → 每层多宽 → 每维算几次 → 一个条目覆盖几个 token 与每元素几字节。

**2. config 与权重冲突时权重赢。** 已知会错的：判型字段（V4 不声明 `kv_lora_rank`，MLA 判据失效）、
`weight_block_size`（对 FP4 专家错 128 倍）、`mtp_layers`（声明 1、权重里 3 块）、
头数乘积当缓存宽度、`head_dim` 只管 QK 而 `v_head_dim` 另有其值（按前者推 `o_proj` 高 50%）。
config 描述模块配置，不描述落盘形状。

**3. 恒定也是信息。** 变量变而被测量不变，**排除**了那个被测量作为变化轴。R30 就是这么定下来的：
压缩比 2/2/2/1 四层而 `compressor.wkv` 输出恒 512，说明比值不作用在宽度上；缓存只有条目数和宽度两根轴，
不是宽度就是长度。记录里原本把同一个事实读成了「所以权重里看不出压缩比在折算什么」。

**4. 覆盖面不等于占比。** 抽样读了 10/163 个分片、某个 dtype 在抽到的层里占 100%，
不能写成「全部层」。抽样产物只回答它被瞄准的那个问题。

**5. 结构规律钉代际。** 「零例外」通常只对一代成立。R28 的那条律在 V4 为真、在 V4.1 两条分句全假，
却渲染在 V4.1 页上。写进记录时带上作用域。

**6. 二手来源标二手，不急着关。** 从实现分析、博客、图里读到的格式与精度，evidence 记 `judgement`，
open question 继续开着。要钉死得读 kernel 或实测显存，那是独立一轮的事。
**可信度不同的东西不要乘进同一个字段** —— 元素数和精度分两处存。

**7. 空结果和「真的没有」在代码里长得一样。** 定向取数一类都没命中时报错退出、不写文件；
零差异版本的 `shapes.json` 是空的，存在性检查用 `names.json`。

**8. 免责声明只免掉它点名的那件事。** 「存在逐层压缩比、本公式未建模」盖不住层数用错和把窗口 KV
当全局 KV —— 那两件和压缩比无关。字段上的 caveat 也不会传播到引用它的派生页面。

**9. 注释不是证据。** 一条注释声称某个坑已经填了，是本仓代价最高的一处 —— 它让人不再去看，
而实际只填了五个张量里的五个。要验就去看代码或数据。

**10. 来源优先级：模型卡 / 技术报告 > 厂商参考实现 > 引擎实现。** 精度与模型结构按厂商发布的说法填。
厂商随仓的 `inference/` 常常自称 demo —— V4.1 的 `inference/README.md` 第一句就是
"A readable reference implementation rather than a production serving engine" —— 它会用**伪量化**代替打包存储：
`fp4_act_quant(x, block, inplace=True)` 的 inplace 分支是 `y = torch.empty_like(z)`（**原 dtype**）、
`x.copy_(y)` 后 `return x`，scale 算了从不返回；真打包成 `float4_e2m1fn_x2` 的是 `inplace=False` 那条。
缓存缓冲区也确实是 BF16（`torch.zeros(...)` 不传 dtype，走 `set_default_dtype`）。照这条链读下去，
V4.1 的 FP4 KV 会被读成 BF16、字节高 3.6 倍 —— 而技术报告 §2.4.4 说得很清楚：FP4 是**落盘格式**，
「reduces storage rather than accelerates matmul」，读出前反量化。本仓差一步就把对的记录改错了，
挡住它的不是任何闸口，是有人记得卡上写的是 FP4。
反过来说，参考实现能回答卡和报告不说的事（缓存布局、算法语义、哪些张量真被用到），但**不能推翻它们说过的数**。
引擎实现连这一档都不算：它可能滞后于厂商发布，也可能独立另选格式。本仓用 vLLM 的 `swa_bytes_per_token`
给 V4.1 的滑窗格式做过旁证，而那个数恰好与误读一致，于是没挡住错误、反而给它背了书 —— 假旁证比没有旁证更糟。

**11. 锚在内侧的闸口只守得住一半。** 凡是拿「本仓实测」当锚的检查 —— 参数量对 HF 的 safetensors
tally、缓存字节对厂商公布值、`weights_release` 对权重清单的 dtype 直方图 —— 都只能查出
**内侧多出来的东西**（记录声明了而清单里没有），查不出**外面有而里面没有的**（厂商发了而记录压根没声明）。
方向是单向的，而「闸口绿了」会被读成两边都查过。

本仓现成的例子：`weights_release` 那道闸能揪出三份通义声明了 FP8 / INT4 而主仓清单里一个都没有，
却**查不出 MiniMax-M3 漏掉了 MXFP8** —— 厂商另发了那个变体，记录从没声明过，于是声明与实测完全自洽，
闸口全绿。要补上这一半，锚必须在外侧（厂商的发布清单、HF 的仓列表），那是另一种取数，不是同一道闸的延伸。

所以：**建一道闸时，先写清它锚在哪一侧、因此守不住什么**，写进那道检查的 docstring 里。
不写的话，下一个人会把「这道闸绿的」当成「这件事查过了」—— 而它只查过一半。

## 完成判据

- 每个报出去的乘积，**每个因子**都写了来源；只验了一个因子的乘积不提交
- `derive.py` 和 `validate.py` 都返回 0（用 `.venv/bin/python`），`--list-judgements` 里的新增项自己看过
- 新写的结构规律带代际作用域；新用的口径在 `cache_basis` / `counting_note` 里有定义
- 二手来源的字段标了 `judgement` 并留了 open question，没有被「顺手关掉」
- 跨代或跨族系的倍数，两侧口径同一套；不同就改成元素口径或干脆不报倍数
